# DESIGN.md — ZHATKA Visual & Interaction Design System

> Companion to `MASTER.md` (behaviour, safety, data) and the design brief (Notion/Ramp-HQ-inspired workspace).
> **Rule of precedence:** `DESIGN.md` decides how things *look and are laid out*. `MASTER.md` decides what things *do* and what may be claimed. Where they collide, §1 records the decision.
> All campus data is SIMULATED. Never copy Notion/Ramp logos, names or assets — only the layout principles.

## 2. Design principles

1. **A workspace, not a dashboard.** Pages read like organised documents: title, short description, tabs, content. No hero banners inside the app.
2. **Quiet by default, loud only for risk.** Neutral greys carry 90% of the UI. Colour appears for state, selection and the primary action.
3. **Safety is visible.** Protected, held, unknown and infeasible states are always labelled and explained, never just coloured.
4. **Honest numbers.** Every figure shows its nature: SIMULATED, POTENTIAL, ESTIMATED, MEASURED (SIMULATED) or PROJECTED.
5. **Flat and bordered.** 1px borders and whitespace instead of shadows and floating cards.
6. **One component, one meaning.** A status chip looks identical everywhere.

### 3.3 Spacing, radius, elevation, motion

| Token | Value |
|---|---|
| Spacing | 4px base; use 4, 8, 12, 16, 24, 32, 48 |
| Radius | 6 chips and tags · 8 buttons, inputs · 10 cards, panels, drawers · 12 dialogs and landing screenshot frame |
| Borders | 1px `--border`; emphasised 1px `--border-strong` |

| Tag | Style | Tooltip |
|---|---|---|
| `SIMULATED` | grey outline | "Demonstration data. Not from real campus systems." |
| `POTENTIAL` | warning tint | "Possible avoidable load. Not verified." |
| `ESTIMATED` | blue-light tint | "Calculated from stated assumptions." |

## 5. Component specifications

| Component | Spec |
|---|---|
| **Button** | 32px tall (36 on forms), 8px radius. *Primary:* `--blue` bg, white text. *Secondary:* white bg, 1px `--border-strong`, `--text`. *Ghost:* transparent, hover `--bg-hover`. *Destructive:* secondary with `--critical-fg` text; becomes filled red only inside a confirm dialog. Disabled: `--bg-secondary`, `--text-disabled`, and the **reason is shown** (inline helper or tooltip). |
| **Input / select** | 32px, 1px `--border-strong`, 8px radius, white. Focus ring. Error: `--critical-line` border + message below with icon. |
| **Slider** | 4px track `--border`, filled portion `--blue`, 16px white thumb with 1px border. Paired with a numeric input; value shown in tabular numerals. |
| **Chip / status badge** | 22px tall, 6px radius, 12px/500, icon 12px + label. One `<StatusBadge state>` component for all states in §3.4. |
| **Stat strip (KPI)** | One bordered 10px container split into 4–6 cells by 1px dividers (not separate floating cards). Cell: 12px label, 28px value + unit, optional tag, optional 12px delta/caption. |
| **Card / panel** | White, 1px border, 10px radius, 16px padding, no shadow. Title 14px/600 with optional right-side action. |
| **Data table** | Header row `--bg-secondary`, 12px/600 uppercase-free labels, 40px rows, 1px row dividers, hover `--bg-hover`. Numbers right-aligned and tabular. Sticky header. Row click opens drawer. Pagination or virtual scroll above 50 rows. Toolbar above: search, filter chips, column count, export. |
| **Filter chips** | 28px pill-ish (6px radius); selected = `--blue-light` bg, `--blue-text`, 1px `--blue` border. |
| **Tabs** | Text tabs with 2px underline; counts as grey suffix. |
| **Drawer** | 480px right panel, white, left border + popover shadow, header with title/ID + close, scrollable body, sticky footer actions. Focus-trapped, `Esc` closes. |
| **Dialog** | 480px, 12px radius, dimmed `rgba(32,33,36,.4)` backdrop. Every confirm dialog contains: **"Simulated action — no real electrical system is affected."** Destructive confirms (Reset) require typing `RESET`. |
| **Banner** | Full-width inside content, 1px border, tinted bg, icon, bold lead + one sentence, optional action link. Variants: info (blue), success, warning, critical. |
| **Toast** | Bottom-right, white, 1px border, 4s auto-dismiss, `aria-live="polite"`. |
| **Stepper** | Horizontal numbered steps, 12px labels; passed = grey check, current = blue, failed = red `x`, not-reached = grey outline. |
| **Empty / loading / error** | Every data view has all three. Empty: 32px grey icon, one-line title, one-line hint, one action. Loading: skeleton rows (grey 8px-radius bars, no spinners over 300ms). Error: critical banner + "Retry" and "Reset demo". |
| **Evidence panel** | Collapsible; key/value list in mono for values; shows source readings with timestamps. |
| **Safety checklist** | Vertical list of ordered checks: `check` green PASS, `x` red FAIL, `minus` grey NOT EVALUATED, each with a 13px detail line. First failing check is outlined. |

### 5.1 Charts (Recharts)

- Series palette (in order): `#3478D4` blue, `#8A94A6` slate, `#4CA56B` green, `#E0A03A` amber, `#8B6FD0` purple. Baseline/previous = dashed `#A3A3A0`.
- Horizontal gridlines only (`--grid`), no vertical lines, no chart border, transparent background.
- Axis labels 12px `--text-secondary`; **units on every axis** (kW, kWh, %). Legend top-left, inline, 12px.
- Tooltip: white, 1px border, 8px radius, tabular numerals, shows unit and data-nature tag.
- Time filters as a segmented control (Today · 7D · 30D · Year) above the chart; the chart and the table must both respond.
- Real state data only. No decorative sparklines, no fake "live" animation.
- Colour-blind safety: lines also differ by dash pattern; bars by order plus labels.

Master–detail. Left 280px list of buildings (name, kW, alert dot, mini consumption bar). Full table (columns per MASTER §7.6: room, building, occupancy [count or UNKNOWN], capacity, power kW, baseline kW, sensor, meter, flags, state) with search, filters (building, state, flag) and a power-vs-baseline bar chart under or beside it that respects the filters. **Room drawer** sections: identifiers · occupancy + freshness age + unknown reason · power vs baseline · schedule and conflict · protected equipment + reasons · maintenance toggle + end time · data quality · active recommendations · current safety evaluation with reason code ("why not?").

### 6.5 Room Bookings

Tabs: **Requests · Schedule · History**. *Requests:* table (requester, room, date/time, purpose, status chip, actions Approve / Reject / Reallocate). Reject needs a comment. Reallocate opens a dialog suggesting free rooms of adequate capacity. *Schedule:* week calendar (time rows, room columns or day columns with a room filter); booked = `--reserved-bg`, occupied = `--blue-light`, conflict = warning stripe. *History:* filterable table incl. cancellations. Every action writes an Activity Log event.

### 6.6 Energy Monitoring

Scope switch (Room · Floor · Building) + time segmented control. Main line/bar chart with baseline; side panel "Unusual consumption" listing HIGH USAGE and EMPTY BUT CONSUMING items with excess kW (each links to its recommendation; wording "possible equipment issue — inspection suggested", never "fault diagnosed"). Table beneath with the same scope.

### 6.7 Emergency Planner (strongest page — MASTER Module 3)

Order, top to bottom:
1. **Scenario controls** (3 inputs: baseline kW, demand multiplier slider 0.5–5, capacity % slider 5–100) + **Reset scenario** + **Run allocation**.
2. **Equation strip** in mono, one line each: `100 kW × 3 = 300 kW` · `100 kW × 50 % = 50 kW` · `300 − 50 = 250 kW deficit` · `50 ÷ 300 = 16.67 % supplied`. Recomputes live.
3. **Severity banner:** NORMAL (success) · CAUTION (warning) · SHORTAGE (warning with red line) · **SEVERE RESOURCE EMERGENCY** (critical tint, 4px `--critical-line` left stripe, icon `siren`). Default scenario must show Severe.
4. **Stat strip:** Baseline · Current demand · Available · Deficit · Utilisation · Supply ratio.
5. **Requested vs allocated by category** (grouped bar P0–P3, kW).
6. **Load priority table.** Five *visibly separate* columns: **Requested · Minimum · Allocated · Reduced/Deferred · Unmet**, plus an inline 8px stacked bar per row (allocated = blue, reduced = amber, deferred = hatched grey). Status chip per load: FULL, REDUCED, AT MINIMUM, DEFERRED, UNSERVED WARNING. Priority shown as P0–P3 chip (P0 and protected rows get the purple PROTECTED chip and a locked-field icon). Editable cells are inline inputs with inline validation messages.
7. **Feasibility panel** · **Unmet-demand panel** · **Per-load explanation list** (priority, why reduced, requested, allocated, unmet, "approval required").
8. **Approval panel** (sticky at page bottom on desktop): optional comment, **Approve plan** / **Reject plan**; after inputs change it shows a grey `SUPERSEDED` state.
9. `emergencyDurationHours` assumption input, labelled "assumption".

**Infeasible state** (e.g. capacity 40 %): replace items 6–8 with a full-width critical panel headed exactly **NO FEASIBLE SAFE ALLOCATION**; text "Mandatory requirements (42 kW) exceed available capacity (40 kW) by 2 kW"; a small conflict table (P0 full, P1 min, P2 min, non-deferrable P3 min, subtotal, capacity); minimum feasible capacity in kW and %; the line "Protected-load rules were preserved; nothing was reduced to fit."; "Escalate to authorised campus electrical operators"; allocation columns read `NOT ALLOCATED`; Approve **disabled with its reason**. Add the permanent footnote: *A software algorithm cannot create electricity or resolve a physically impossible capacity situation.*

### 6.8 Data Integrity (MASTER Module 2)

Tabs: Daily · Weekly · Monthly · Yearly. Top-right: **Export CSV / PDF** (CSV neutralises formula-leading characters; PDF is a clean print layout of the current view with a SIMULATED footer). ### 6.10 ZHATKA Intelligence

Tabs: **Recommendations · Safety · Projections**.

## 7. Content and microcopy

- Sentence case everywhere. Plain, calm, specific: "Occupancy cannot be verified because the sensor is offline." not "Alert!".
- Units always shown: kW (power), kWh (energy); never mixed. Times in Asia/Kolkata, stored UTC.
- Words to avoid: AI-powered, learns, real-time (unless true), smart-saves, guaranteed, diagnosed, authentication (for the demo login).
- Emoji: none in the product UI.
- Disabled actions always say why.

---

## 8. Accessibility

- Contrast ≥4.5:1 for text, ≥3:1 for UI borders needed to identify controls; verify every chip pairing in §3.1.
- Full keyboard operation: logical tab order, visible focus, `Esc` closes drawers/dialogs/popovers, arrow keys in tabs and menus.
- Landmarks (`nav`, `main`, `aside`), table headers with `scope`, dialogs with `aria-modal` and focus return.
- Alerts and toasts use `aria-live`; critical banners `role="alert"`.
- Charts have a text summary and a "View as table" toggle.
- Honour `prefers-reduced-motion` and 200% zoom without horizontal page scroll.

## 10. Do / Don't

| Do | Don't |
|---|---|
| Use whitespace and 1px borders to group content | Wrap everything in floating, shadowed, rounded cards |
| Keep one blue for action and selection | Use gradients, glassmorphism, neon or large colour blocks |
| Label every number's nature | Present simulated readings as live measurements |
| Show UNKNOWN as hatched and dashed with "?" | Draw UNKNOWN as empty or zero |
| Explain disabled and held actions | Hide or grey out controls silently |
| Keep page titles ≤24px | Put giant headings on every page |
| Use real state in charts | Add decorative charts, fake live pulses or stock imagery |
| Copy layout principles from Notion/Ramp | Copy their logos, names or assets |
